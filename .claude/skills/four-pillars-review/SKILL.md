# four-pillars-review

仕様駆動開発における4本柱レビューの**方法論本体**。`review-spec` Skill から内部参照される。

詳細プロンプトは [prompts/four-pillars.md](../../../prompts/four-pillars.md) を参照。

## なぜ4本柱なのか

要件定義書の質は単一の尺度では測れない。4つの独立した観点で測定し、それぞれに固有のチェック手法を当てる必要がある。

## なぜ「この順序」なのか

```
明確性 → 完全性 → 一貫性 → 実装可能性
```

| 順番 | 柱 | 前提 | 順序の理由 |
|------|-----|------|------------|
| 1 | 明確性 | なし | 曖昧な文は読み手で解釈が分かれ、後段の判定自体が成立しない |
| 2 | 完全性 | 明確性 | 曖昧な要件では「何が抜けているか」を判定できない |
| 3 | 一貫性 | 明確性＋完全性 | 明確かつ揃った要件であってこそ、内部矛盾を比較判定できる |
| 4 | 実装可能性 | 1〜3すべて | 明確・完全・一貫した要件を前提に、現実の制約で検証する最終ゲート |

**順序の入れ替えは禁止**。例えば実装可能性を先に判定すると、曖昧な要件を「実装不可能」と誤判定するか、「曖昧なまま実装」を許容してしまう。

## 各柱の具体手順

### 柱1: 明確性 (Clarity)

> 出典: `app.py` PROMPT_AMBIGUITY の「検出する曖昧性の種類」6項目

1. 主語の省略・指示語の多用（「それ」「この」「当該」）
2. 循環構造・境界条件の不明確さ（「最後の次」「端の場合」）
3. 終了条件・例外条件の欠落
4. 用語の揺れ（同一概念に複数の名称）
5. 暗黙の前提（記述されていない前提条件）
6. 数量・順序・方向の曖昧さ

→ 出力: 曖昧箇所リスト（箇所・種別1〜6・問題・影響）＋形式的補完案

### 柱2: 完全性 (Completeness)

> 出典: `app.py` PROMPT_REVIEW の評価観点2

- **WhyとWhatが明確か**
  - Why: 課題・背景・KPI・成功指標の記述有無
  - What: 機能・入出力・データ型・境界条件・エラー処理の記述有無

→ 出力: 不足項目リスト＋補完記述案

### 柱3: 一貫性 (Consistency)

> 出典: `app.py` PROMPT_REVIEW の評価観点3

- **矛盾・用語の揺れがないか**
  - 用語の揺れ: 同一概念に複数の名称が使われていないか
  - 値の矛盾: 数値・閾値が箇所によって食い違っていないか
  - 論理の矛盾: 同時に成立しない要件が共存していないか

→ 出力: 矛盾箇所の対照表

### 柱4: 実装可能性 (Feasibility)

> 出典: `app.py` PROMPT_REVIEW の評価観点4

- **技術的に実現可能か**
  - 技術的実現性: 必要な技術が既存・成熟しているか
  - 性能的実現性: 数値目標が物理制約内か
  - テスト実現性: 検証可能な形で要件が定義されているか

→ 出力: 実現困難要件＋代替案

## 単一柱モード

ユーザーが「明確性だけチェックして」のように単一柱を指定した場合、その柱だけを実行する。
ただし、その柱が前提とする上位柱が満たされない可能性を警告する。

## 透明性出力（毎回必須）

各柱の評価を実行するたびに、**評価前の方針宣言 → 評価実施 → 評価後の推論ログ** の順で出力する。
目的：人間がAIの判断プロセス（何をどう解釈して評価したか）を確認し、誤りや暗黙知の使用を特定できるようにする。

### ステップA: 評価前の方針宣言（各柱の評価を始める前に必ず出力）

この柱をどう解釈し、どう扱うかをAIが事前に宣言する。
評価結果ではなく「評価の進め方の設計」を示すブロック。

```
### 📋 柱N: [柱名] — 評価方針宣言

**この仕様書に対するこの軸の解釈**:
[この軸（例: 明確性）を、この仕様書の文脈でどう定義して適用するか。
 一般的な定義と、この文書固有の事情があれば両方を記載。]

**チェック項目の優先順位とその理由**:
| 優先順位 | チェック項目 | なぜこの順序か |
|---------|------------|-------------|
| 1位 | [例: 未定義の用語] | [例: この仕様書はドメイン用語が多く、定義なしでは後続の判定が成立しないため] |
| 2位 | [例: 数量・閾値の曖昧表現] | [例: 性能要件セクションが存在するため数値の明確化が重要] |
| 3位〜 | … | … |

**「問題あり」とみなす判断閾値**:
[何をもってこの柱での「問題あり」と判断するかの基準を宣言する。
 例: 「2人以上の読み手が異なる解釈をしうる表現を問題ありとする」
 例: 「後続の実装工程で確認作業が発生するレベルの曖昧さを問題ありとする」]

**重点スキャン対象セクション**:
[この仕様書の中で、この柱の観点から特に注意深く読むべきセクションと理由。]

**スキップ・軽視するセクション**（あれば）:
[評価対象から除外する箇所と、その理由。なければ「なし」と記載。]
```

### ステップB: 評価後の推論ログ（各柱の評価結果の直後に出力）

```
### 🔍 柱N: [柱名] — 評価推論ログ

**評価判断テーブル**:
| チェック項目 | 判定 | 根拠種別 | 根拠の詳細 |
|------------|------|---------|-----------|
| [項目名] | ✅正常 / ⚠️要改善 / ❌問題あり | 仕様内 / 暗黙知 / 両方 | [具体的な根拠] |

**優先度割り当て**:
| 指摘ID | 優先度 | 理由 |
|--------|--------|------|
| [例: C1-001] | HIGH | 後続の柱（完全性）の判定前提となるため |
| [例: C1-002] | LOW | 表記ゆれのみで解釈に実害なし |

**方針宣言との差異**（事前宣言と実際の評価がズレた場合のみ記載）:
[例: 「重点スキャン対象として§3を挙げたが、実際には§5に主要な問題が集中していた。
　　  理由: 事前に予期できなかった用語の重複使用が§5に存在したため。」]

**暗黙知使用箇所**:
この柱の評価で仕様外の知識・一般慣習・設計原則を使用した場合に列挙する。
なければ「なし」と記載。
- [例: 「トークンの有効期限はセキュリティ標準として24時間以内が推奨」という一般知識を使用]
```
