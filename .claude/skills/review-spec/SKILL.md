# review-spec

仕様書を4本柱（明確性・完全性・一貫性・実装可能性）でレビューするSkill。
詳細な評価順序・依存関係は `[[four-pillars-review]]` Skill に従う。

## いつ使うか

- ユーザーが「レビューして」「改善提案して」と仕様書をレビュー依頼したとき
- `/specflow-pipeline` の第2ステップ（曖昧性検出後）として呼ばれたとき
- PR作成前の品質ゲートとして

## 手順

1. レビュー対象の仕様書（パス or 本文）を取得する
2. **[透明性] 使用Skill出力**：このSKILL.mdの全文をコードブロックで出力する（後述「透明性出力」参照）
3. [prompts/four-pillars.md](../../../prompts/four-pillars.md) と [`[[four-pillars-review]]`](../four-pillars-review/SKILL.md) の方法論に従い、**順序を厳守** して評価する：
   - 柱1: 明確性 → 完了するまで柱2に進まない
   - 柱2: 完全性 → 完了するまで柱3に進まない
   - 柱3: 一貫性 → 完了するまで柱4に進まない
   - 柱4: 実装可能性
4. 各柱で以下を順番に実行する：
   - **[透明性・評価前] 方針宣言を出力する** — この軸をどう解釈しチェック項目をどの順序で扱うかを宣言（`[[four-pillars-review]]` ステップA参照）
   - チェック項目を宣言した優先順位で走査
   - 該当箇所を引用して指摘
   - 改善案を提示
   - **[透明性・評価後] 評価推論ログを出力する**（`[[four-pillars-review]]` ステップB参照）
5. 統合フォーマットで出力：
   ```
   ## レビュー結果
   ### 1. 明確性
   ### 2. 完全性
   ### 3. 一貫性
   ### 4. 実装可能性
   ## 改善提案
   ## 改善済み仕様書
   ```
6. **[透明性] 推論ログ・暗黙知追記を出力する**（後述「透明性出力」参照）

## 重要な制約

- 4本柱は **必ずこの順序で** 評価する。順序を入れ替えると前提が崩れる
- 柱1で曖昧性が多数残る場合、まず `[[detect-ambiguity]]` を実行してから戻ってくることを提案する
- 「改善済み仕様書」は省略せず全文を出力する

## 透明性出力（毎回必須）

このSkillを実行するたびに、以下の3ブロックを出力する。

### ブロック1: 使用Skill（実行冒頭）

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【使用Skill: review-spec】
（このSKILL.mdの全文をここに貼り付け）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### ブロック2: 柱ごとの評価根拠ログ（各柱の直後）

各柱の評価結果の**直後**に、以下の形式で記録する。
「なぜその指摘をしたか」「仕様書のどこを根拠にしたか」「仕様外の知識を使ったか」を明示する。

```
### 📋 柱N 評価根拠ログ

| チェック項目 | 判定 | 根拠種別 | 根拠の詳細 |
|------------|------|---------|-----------|
| 主語の省略 | 問題あり | 仕様内 | §1.2「利用者は〜」の主語が不明確 |
| 境界条件（上限） | 問題あり | 暗黙知 | MAX値の記述なし。Webシステムでは上限定義が必要と判断 |
| エラー定義 | 問題なし | 仕様内 | §3.4にエラーコード一覧が定義済み |

**優先度判断**：
- HIGH（柱の根幹に関わる指摘）: [指摘番号のリスト]
- MEDIUM（改善推奨）: [指摘番号のリスト]
- LOW（任意対応）: [指摘番号のリスト]

**優先度の判断根拠**: [なぜそのように優先度を割り当てたか]
```

### ブロック3: 暗黙知追記サマリ（出力末尾）

「改善済み仕様書」に加筆した内容のうち、**仕様書に明記されていないもの**を一覧化する。

```
## 暗黙知追記サマリ（review-spec）

| 追記箇所 | 追記内容の概要 | 使用した暗黙知・前提 | 削除・変更する場合の対応 |
|---------|--------------|-------------------|----------------------|
| §2.1 | レートリミット要件を追加 | APIには一般的にレートリミットが必要 | SKILL.md「重要な制約」に「非機能要件は追記しない」と明記 |
| §3.4 | ロールバック手順を追記 | DBトランザクションの標準実装から推論 | prompts/four-pillars.mdの柱4チェック項目から「ロールバック」を除外 |
```
